# Architecture

ScreenRecorder is a Rust desktop application. `eframe` 0.37 supplies the Windows UI, text and existing OpenGL presentation; `windows-sys` exposes GDI. `windows` supplies WASAPI, COM and Media Foundation. `image` supplies JPEG encoding/decoding and CPU resampling. There is no external media process or runtime service. The renderer has not been changed or runtime-certified by this audio/export extension; see the incomplete rendering gate below.

## Boundaries and lifetime

- `capture::FrameSource` is the frame boundary. The Windows `Source` owns a screen DC, memory DC and top-down DIB. It uses `BitBlt` into the reusable DIB and converts BGRA to RGB. GDI resources are restored/released on every exit path. The source is created and destroyed on the capture worker after the Start action; it is never constructed by a test.
- `recorder` drives a single synchronous capture/encode/write worker. There is no unbounded queue of images. Target fps determines the next deadline; slow work does not enqueue stale captures. Monotonic timestamps exclude paused time. Pause waits on a bounded command channel with a 250 ms stop-shortcut check; it does not sample cursor coordinates or acquire frames.
- `timeline` maps absolute Windows QPC timestamps in 100 ns units to active recording time. Pause/resume boundaries store cumulative active time; lookup uses binary search. Audio packets crossing start, pause or stop boundaries are split/clipped before storage. Video obtains timestamps from the same clock.
- `audio::Session` starts one MTA worker only after the Start action chooses microphone and/or system audio. It opens the corresponding default WASAPI endpoints in shared mode, with `AUDCLNT_STREAMFLAGS_LOOPBACK` for the render endpoint. Each client has a one-second buffer. While active, a bounded 10 ms receive wait drives packet draining; while paused, clients stop and the worker waits at 50 ms intervals for resume/stop. No UI timer or idle device worker exists. Every acquired packet is released even if conversion/writing fails. Errors stop the shared recording and completed journals are flushed.
- `audio` normalizes supported native float/PCM layouts to timestamped stereo 48 kHz float journals. Each packet's output grid is anchored to the shared clock, rather than resetting resampling phase at packet boundaries. Mixing reads at most 100 ms per track, inserts silence for absent spans, applies per-track gain and halves both tracks when two are present. Conversion/downmixing is CPU code; no audio playback API is used.
- `project` appends JPEG frames and cursor metadata, validates dimensions/timestamps/lengths and builds a bounded index when opening. It syncs data every 15 frames and at finalization. A failed append attempts truncation to the last complete frame; a failed capture still flushes completed frames. The reader ignores an incomplete trailing header or body without modifying the source. This is recovery of completed writes, not a guarantee against arbitrary filesystem/power-loss corruption.
- `editor` separates source media from edit decisions. Automatic zoom segments come from sampled left-click edges; nearby clicks extend the same focus segment. Smoothstep entry/exit ramps animate crop position/scale. Cursor highlight, standardized pointer and click rings are applied after crop/resampling. Preview and export call the same compositor.
- `avi` writes AVI 1.0 with a single `vids/MJPG` stream and an `idx1` index. Export decodes at most one source frame at a time, repeats it for constant-rate output if necessary, and writes an adjacent `.avi.partial`. Successful finalization atomically publishes a new destination with `MoveFileW` without replacing a preexisting file. Errors/cancellation remove the partial file; an abrupt process kill may leave it for manual cleanup.
- `mp4` initializes COM/Media Foundation on the export worker and uses `IMFSinkWriter` with an exclusively created `IMFByteStream`. CPU conversion produces top-down BT.709 limited-range NV12; odd edges pad to even dimensions. Windows software transforms encode H.264 and optional 48 kHz stereo AAC. Video and audio samples interleave, with integer 100 ns timing and a shortened final video sample. Source audio trim uses the same in/out points. The sink is finalized/released before filesystem sync and atomic publication. A creation guard removes only a newly created partial if configuration fails; existing partial files remain untouched. Cancellation is observed between samples; it cannot interrupt an in-flight Windows encoder/finalization call.
- `settings` stores only recording defaults and startup-update preference. Edits/settings use a complete temporary write, sync, then replacement. A stale temporary file causes a useful error instead of being silently overwritten.
- `updater` owns HTTPS, semantic version selection, compatible asset selection, digest/PE checks, staging and the helper mode. It never runs in the test suite. Pure release/checksum selection and artificial PE verification are tested independently.

There is one media worker, at most one audio worker during recording, and at most one update worker. UI results use an eight-message bounded channel. Progress is throttled to roughly four updates per second and stale progress can be dropped. Worker completion explicitly wakes the UI; no idle timer requests continuous repainting. Slider changes coalesce and preview generation IDs reject stale results. Heavy frame processing, indexing, capture, network and downloads run away from the UI; small settings/edit JSON saves occur on their explicit UI actions.

Closing during recording/export requests cancellation and waits for the media completion event before destroying the window. Closing during update download requests cancellation and waits for completion without launching the helper. A normal idle close does not wait for a metadata-only startup request. There is no tray or hidden persistent process. Windows shutdown/process termination can interrupt finalization; reopening `.srec` attempts tail recovery.

The pinned eframe native event-loop source was inspected: `check_redraw_requests` explicitly selects `Wait` without a repaint deadline and `WaitUntil` for deadlines. Its hidden-window path invokes `App::logic` without `App::ui`. UI progress only wakes for changed status; static layout has no recurring repaint request. These are source observations, not a runtime gate pass. Visible/idle/minimized/restore frame counts, CPU/GPU cost, actual backend operation and latency remain unmeasured because GUI launches are prohibited. The user prefers verified CPU rendering for ordinary 2D utilities; this extension retains the existing Glow presenter rather than introducing an unverified renderer migration alongside audio work. A future authorized visual test must apply the performance gate and evaluate that remaining renderer choice.

## SREC version 1 layout

All scalar fields are little-endian. File header: 8-byte `SREC0001`, `u32 width`, `u32 height`, `u32 fps` (20 bytes). Repeating frame records have a 25-byte header: `u32 jpeg_length`, `u64 time_us`, `f32 cursor_x`, `f32 cursor_y`, `u8 flags` (bit 0 visible, bit 1 left-button down edge), four reserved zero bytes, followed by JPEG data. Timestamps are strictly increasing. Coordinates are finite and normalized even when invisible.

The reader caps the file at 16 GiB, frames at 200,000, individual JPEGs at 32 MiB, dimensions at 4096 × 2160, time at 24 hours and decoded-frame allocation at 128 MiB. The index stores metadata/offsets, not frame pixels. JPEG dimensions must match the project header. Edit sidecars are at most 1 MiB and contain at most 2,000 manual zoom segments.

## Audio journal version 1

`<project>.mic.saudio` and `<project>.system.saudio` are discovered beside the video project. Their little-endian 16-byte header contains `SRAPCM01`, `u32 48000` and `u32 2`. Each packet contains `u64 start_frame`, `u32 frame_count`, then interleaved stereo `f32` data. Sparse positions represent silence. The reader rejects overlapping packets, invalid lengths and out-of-range/overflowing timestamps, ignores an incomplete trailing packet and propagates a recovery warning to the project. At read time, nonfinite samples are rejected. Writer recovery truncates an incomplete append where possible and syncs every 100 packets plus shutdown.

Limits: one second per packet, 1,000,000 indexed packets and 8 GiB per track, at most two tracks, and a 24-hour timeline. No whole recording is loaded into RAM. New audio/gain fields have serde defaults, so old settings and video-only edit decisions remain readable. Move all project sidecars together; the old 0.1 application does not understand or export audio journals.

## Design tradeoffs

GDI remains the visible-pixel capture boundary, including occlusion; it is not isolated Windows Graphics Capture/Desktop Duplication. MJPEG AVI remains a silent compatibility export. MP4 uses installed Windows components with hardware transforms disabled; Windows N requires Media Feature Pack. Audio uses default endpoints without changing device/volume/privacy settings. A fixed endpoint is not automatically switched mid-recording. Protected system audio can be excluded by Windows. Linear resampling, click sampling and AAC padding are intentionally documented limits; real hardware quality/clock drift have not been validated.
